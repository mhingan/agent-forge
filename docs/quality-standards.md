# AgentForge quality standards

AgentForge is designed as a reusable starting point for real engineering work. It does not claim to replace project architecture, organizational policy, expert review, or testing in the target environment.

## Content quality

Every canonical skill should have:
- A specific capability and activation description.
- A clear scope and non-goals.
- Required context to inspect before acting.
- An ordered, actionable procedure.
- Domain-specific decisions and failure cases.
- Security, privacy, and permission boundaries.
- Verification and acceptance criteria.
- Explicit deliverables and completion reporting.
- Anti-patterns or unsafe approaches to avoid.

Every specialist agent should have:
- A bounded role and mission.
- Responsibilities and working method.
- Expected inputs/outputs and delegation interface.
- A conservative default posture.
- Explicit side-effect/approval boundaries.
- A verifiable completion standard.

Rules should be concise enough to remain useful as persistent context, with domain-specific detail placed in skills or references. Workflows should describe a sequence with gates and stop conditions. Commands should specify purpose, inputs, procedure, output, and boundaries.

## Progressive disclosure

The root SKILL.md is the activation and operating guide. Deep templates and large checklists belong in linked reference files. This keeps common context focused while allowing an agent to load detailed material when the task requires it.

## Portability

- Canonical skills follow Agent Skills naming and metadata requirements.
- Canonical agent definitions stay provider-neutral.
- Native file formats are generated by adapters.
- Compatibility claims must be backed by official product documentation and tested renderers.
- Unsupported behavior must be documented as a limitation, not approximated silently.

## Security and safety

- No secrets or private data.
- No silent elevation of tool permissions.
- No unattended destructive production action.
- No execution of skill scripts during validation or installation.
- Least-privilege examples for read-only agents.
- Retrieved and external content is untrusted data, not privileged instructions.

## Machine-readable metadata

All JSON files must:
- Parse as strict JSON (no comments, trailing commas, NaN/Infinity, or duplicate keys).
- Use two-space indentation.
- Preserve Unicode characters (UTF-8, no unnecessary escaping).
- End with exactly one trailing newline.
- Have stable, reviewable object structure.
- Be consistent with related catalogs, schemas, adapters, and source files.

Run `python scripts/format_json.py --check` and `python -m agentforge validate --strict`.

## Verification standard

A repository change is ready when:
- Canonical files are updated.
- Catalog paths/names/descriptions are consistent.
- Embedded package data matches canonical sources.
- Agent outputs parse in their respective formats.
- Install/uninstall behavior does not overwrite unmanaged or locally modified files.
- Tests pass and CI checks the claimed behavior.
- Documentation and changelog describe the user-visible change.

## Honest claims

A successful parser test does not prove a provider will discover a generated file. A static accessibility scan does not prove WCAG conformance. A read-only agent prompt is not a sandbox. A backup job is not a verified restore. A code review is not a complete security audit. Claims must match the evidence and scope.
